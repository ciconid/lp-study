## Pregunta 8
> ¿Qué chequeos de tipos puede realizar un lenguaje en torno al tipo unión? ¿Qué sucede en caso de unión discriminada?

## Respuesta

Un **tipo unión** permite que una misma ubicación de memoria contenga valores de tipos distintos en distintos momentos de ejecución.

> *"A union is a type whose variables may store different type values at different times during program execution."*
> — sebesta-chapter6.pdf (p. 61)

El problema central de las uniones es el **chequeo de tipos**: el lenguaje debe poder saber qué variante está actualmente almacenada para poder verificar si el acceso es válido.

> *"The problem of type checking union types [...] is their major design issue."*
> — sebesta-chapter6.pdf (p. 61)

### 1) Uniones libres (*free unions*)

En lenguajes como C y C++, las uniones no tienen soporte de chequeo de tipos a nivel de lenguaje. Eso significa que el compilador no puede determinar qué campo de la unión está activo en cada momento.

> *"C and C++ provide union constructs in which there is no language support for type checking."*
> — sebesta-chapter6.pdf (p. 61)

> *"The unions in these languages are called free unions, because programmers are allowed complete freedom from type checking in their use."*
> — sebesta-chapter6.pdf (p. 61)

En una unión libre, un acceso puede compilar aunque sea semánticamente incorrecto. Por ejemplo, si se cargó un entero y luego se lee el mismo contenido como `float`, el sistema no puede verificar que esa interpretación sea válida.

> *"This last assignment is not type checked, because the system cannot determine the current type of the current value of el1, so it assigns the bit string representation of 27 to the float variable x, which, of course, is nonsense."*
> — sebesta-chapter6.pdf (p. 62)

### 2) Uniones discriminadas

Para que una unión pueda ser chequeada, el lenguaje debe incluir una **marca de tipo** asociada a la variante activa.

> *"Type checking of unions requires that each union construct include a type indicator. Such an indicator is called a tag, or discriminant, and a union with a discriminant is called a discriminated union."*
> — sebesta-chapter6.pdf (p. 62)

Con ese tag, el lenguaje puede verificar en ejecución qué variante está activa y controlar que el acceso corresponda a esa variante. Eso habilita chequeo de tipos dinámico sobre la unión.

Sebesta aclara además que estas uniones discriminadas están soportadas por lenguajes como ML, Haskell y F#.

> *"The first language to provide discriminated unions was ALGOL 68. They are now supported by ML, Haskell, and F#."*
> — sebesta-chapter6.pdf (p. 62)

### Qué chequeos puede hacer el lenguaje

En torno a las uniones, el lenguaje puede:
- Verificar que el acceso se haga con la variante correcta, si existe un discriminante.
- Rechazar o señalizar accesos incompatibles cuando el tag no coincide.
- En uniones libres, no puede hacer ese chequeo y la responsabilidad recae en el programador.

Scott resume esto al distinguir entre uniones etiquetadas y no etiquetadas: para las segundas no hay una solución aceptable de chequeo en tiempo de ejecución comparable a la de una unión discriminada.

> *"For a tagged variant record (discriminated union) type, the descriptor is a bit more complicated: it must contain a list of values (or ranges) for the tag, together with a table for the corresponding variant. For untagged variant records, there is no acceptable solution."*
> — scott-chapter7.pdf (p. 71)

### Conclusión

- En una **unión libre**, el lenguaje no puede garantizar el chequeo de tipos del valor almacenado; por eso el acceso incorrecto puede pasar desapercibido.
- En una **unión discriminada**, el tag permite al sistema determinar la variante activa y realizar chequeos de tipos dinámicos más seguros.
- Por eso, las uniones discriminadas son la versión más segura y más dura del constructo unión.
